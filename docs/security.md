# Безопасность

Главный принцип: сервер не может прочитать секреты. Всё шифрование выполняется на клиенте, а сервер хранит шифротексты и проверяет доступ.

## Схема ключей

```
masterKey = Argon2id(пароль, соль, параметры)   # только на клиенте
authKey   = HKDF(masterKey, "auth")             # отправляется на сервер при входе
encKey    = HKDF(masterKey, "encryption")       # AES-256-GCM, только на клиенте
hmacKey   = HKDF(masterKey, "blind-index")      # blind index, только на клиенте
```

Сервер хранит `SHA-256(authKey)`. Из `authKey` нельзя получить ни `masterKey`, ни `encKey`, поэтому ни сервер, ни утёкшая база, ни перехваченный `authKey` не позволяют расшифровать секреты.

Соль и параметры Argon2id хранятся у каждого пользователя и приходят клиенту перед входом. По умолчанию `t=3, m=64 MiB, p=4` (RFC 9106). Другие параметры задаются флагами `--kdf-time` (1–10) и `--kdf-memory` (19–1024 MiB) у `auth register` и `auth passwd`: больше — дороже перебор при утечке базы, но медленнее каждый вход. Клиент отказывается работать с параметрами вне этих границ, чтобы подменённый сервер не мог ни ослабить деривацию, ни заставить клиент считать часами.

Секрет хранится так:

- **Данные** — JSON с именем, типом и содержимым, дополненный до размера, кратного 256 байтам, и зашифрованный AES-256-GCM ключом `encKey`.
- **Blind index** — `HMAC-SHA256(hmacKey, имя:тип)`. По нему сервер находит секрет, не зная имени.
- **Комментарий** (metadata) шифруется вместе с данными.

## Модель угроз

| Угроза | Защита |
| --- | --- |
| Утечка базы или компрометация сервера | В базе шифротексты и `SHA-256(authKey)`. Остаётся офлайн-перебор паролей ценой Argon2id на каждую попытку |
| Перехват трафика | TLS с собственным CA. Без TLS клиент подключается только с `GOPHKEEPER_INSECURE=true` |
| Онлайн-перебор паролей, массовая регистрация | Лимит частоты запросов к аутентификации с одного IP, закрытая регистрация |
| Заполнение диска сервера | Квоты на размер и число секретов у пользователя |
| Кража файла сессии | Токен живёт 1 час, его можно отозвать. Без мастер-пароля токен даёт доступ только к шифротекстам, но позволяет удалить или перезаписать секреты |
| Подмена секрета сервером | После расшифровки клиент сверяет имя и тип внутри секрета с blind index записи. Расхождение — ошибка «нарушена целостность» |
| Перебор логинов | Для несуществующего логина сервер возвращает стабильную фиктивную соль, вход отвечает одинаково при неверном логине и неверном пароле |
| Опечатка в мастер-пароле | Пароль проверяется на сервере до шифрования, и секрет не сохранится под ключом от неверного пароля |
| Подбор длины пароля по размеру | Открытый текст дополняется до кратного 256 байтам |

Ошибка «нарушена целостность» при `secret get` или `secret list` означает, что сервер вернул не тот секрет, который запрашивался, — признак компрометации сервера.

## Сессии

После входа клиент хранит токен в файле сессии (`~/.gophkeeper/session`, права `0600`). Каждая операция с секретами проверяет мастер-пароль на сервере и получает новый токен, поэтому срок жизни можно держать коротким (`TOKEN_TTL`, по умолчанию 1 час).

Отзыв раньше срока, сервер проверяет его при каждом запросе:

- `auth logout` — токен этого устройства;
- `auth logout --all` — все токены пользователя. Используйте, если устройство потеряно или файл сессии мог утечь;
- `admin revoke-sessions` — то же самое со стороны администратора;
- смена пароля и восстановление базы из копии тоже завершают все сессии.

Десктоп-приложение держит ключи в памяти только пока хранилище разблокировано и блокируется, когда сервер отзывает сессию.

## Смена пароля

От пароля зависят ключ шифрования и blind index, поэтому `auth passwd`:

1. скачивает все секреты и расшифровывает их текущим ключом с проверкой целостности;
2. генерирует новую соль и выводит ключи из нового пароля;
3. шифрует секреты заново, пересчитывает blind index и отправляет всё одним потоком.

Сервер проверяет текущий пароль и заменяет соль, параметры, хеш и все секреты в одной транзакции: при любой ошибке ничего не меняется. Если в это время другое устройство изменило секреты, смена отменяется с просьбой повторить — иначе такой секрет остался бы со старыми ключами. После смены все сессии завершаются.

Смена пароля — это и способ перейти на более сильные параметры Argon2id, и действие на случай, если пароль мог утечь.

## Десктоп-приложение

- Ключи держатся в памяти, только пока хранилище разблокировано. Оно блокируется вручную, при сворачивании окна, после бездействия и при отзыве сессии.
- Содержимое секрета запрашивается только при открытии; пароли и CVV скрыты, пока их не показали. Скопированное значение стирается из буфера обмена через 30 секунд.
- Интерфейс встроен в бинарь, строгий Content-Security-Policy не даёт загрузить что-либо извне.
- В релизной сборке нет DevTools и контекстного меню браузера, а брошенный в окно файл не открывается. CI проверяет, что приложение собрано без `debug` и `devtools`.
- Wails при панике пишет в лог весь вызов вместе с аргументами. Приложение вырезает из логов содержимое вызовов, поэтому мастер-пароль и секреты туда не попадают.

## Экспорт

Файл экспорта (`.gkx`) шифруется отдельным паролем экспорта: ключ — Argon2id с собственной солью, шифр — AES-256-GCM. Мастер-пароль и сервер для расшифровки не нужны, поэтому файл можно импортировать в любую учётку на любом сервере. Пароль экспорта — не короче 8 символов; лучше взять парольную фразу (`gophkeeper generate --words 6`) и хранить её отдельно от файла.

## Генератор паролей

Пароли и парольные фразы генерируются на клиенте из `crypto/rand` без статистического перекоса. В пароле есть символ каждого выбранного набора. Парольная фраза составляется из словаря [EFF Large Wordlist](https://www.eff.org/dice) (7776 слов, CC BY 3.0 US): шесть слов дают около 77 бит, а запомнить и набрать их легко — так удобно задавать мастер-пароль.

`generate` выводит в stdout только пароль, оценку стойкости — в stderr, поэтому пароль можно передать дальше: `gophkeeper generate | xclip -selection clipboard`.

## Известные ограничения

- Сервер может вернуть **старую версию** того же секрета или скрыть секрет из списка. Без хранения состояния на клиенте это не обнаружить.
- Сервер видит метаданные: число секретов, время создания и изменения, примерный размер. Большой файл от короткого пароля отличить можно.
- Регистрация отвечает «логин занят», поэтому через неё можно проверить, существует ли логин. Закрытая регистрация это исключает.
- Пользователи, созданные до появления настраиваемых параметров Argon2id, остаются на `t=1`, пока не сменят пароль. По этим параметрам можно понять, что логин существует и создан давно.
- Забытый мастер-пароль не восстановить: ни пользователь, ни администратор не могут расшифровать секреты без него.
