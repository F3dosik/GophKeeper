# Развёртывание сервера

Сервер, PostgreSQL, миграции и резервное копирование запускаются через Docker Compose. Нужны Docker с Compose, OpenSSL, `make` и `git`.

```bash
git clone https://github.com/F3dosik/GophKeeper.git && cd GophKeeper
cp .env_example .env      # заполнить, см. ниже
make certs                # сертификаты TLS
make docker-up            # скачать образ сервера и запустить
make docker-down          # остановить (данные в volume сохраняются)
```

Сервер не компилируется на машине: `make docker-up` скачивает готовый образ из [GitHub Container Registry](https://github.com/F3dosik/GophKeeper/pkgs/container/gophkeeper), его собирает CI (см. [Образ сервера](#образ-сервера)). Поэтому хватает небольшого VPS: в работе весь стек занимает около 100 МБ памяти, при интенсивной работе с крупными файлами — до 350 МБ.

## Настройка (`.env`)

Шаблон — [`.env_example`](../.env_example). Обязательны параметры базы и `JWT_SECRET`, остальное можно оставить по умолчанию.

| Переменная | Описание | По умолчанию |
| --- | --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Учётка и имя базы для контейнера PostgreSQL | — |
| `DATABASE_URL` | DSN для сервера, например `postgresql://gophkeeper:пароль@db/gophkeeper?sslmode=disable` | — |
| `DB_PORT` | Порт PostgreSQL на `127.0.0.1` хоста | `5433` |
| `JWT_SECRET` | Не короче 32 символов, например `openssl rand -hex 32`. Из него выводятся ключ подписи токенов и фиктивные соли | — |
| `TOKEN_TTL` | Время жизни токена | `1h` |
| `SERVER_PORT` | Публичный порт gRPC | `50051` |
| `LOG_LEVEL` | `development` или `production` | `development` |
| `TLS_CERT_FILE`, `TLS_KEY_FILE` | Сертификат и ключ сервера внутри контейнера | `/certs/server.crt`, `/certs/server.key` в шаблоне |
| `AUTH_RATE_LIMIT` | Запросов к `GetSalt`/`CreateUser`/`Login` в минуту с одного IP | `30` |
| `AUTH_RATE_BURST` | Таких запросов подряд с одного IP | `20` |
| `SECRET_MAX_SIZE` | Размер зашифрованного секрета, байт (не больше 32 MiB) | `1048576` |
| `SECRET_MAX_COUNT` | Секретов у одного пользователя | `1000` |
| `REGISTRATION_ENABLED` | Регистрация на публичном порту | `true` |
| `ADMIN_PORT` | [Административный порт](#регистрация-и-администрирование); пусто — выключен | — |
| `TEMP_PASSWORD_TTL` | Срок действия временного пароля | `24h` |
| `BACKUP_INTERVAL` | Период [резервного копирования](#резервные-копии) | `24h` |
| `BACKUP_KEEP` | Сколько последних копий хранить | `14` |

Пояснения к лимитам:

- Каждая операция с секретами проверяет мастер-пароль и обращается к `Auth` дважды, поэтому при значениях по умолчанию с одного IP проходит 10 операций подряд и около 15 в минуту. Если клиенты ходят через общий NAT, лимиты стоит поднять.
- Файлы хранятся в base64 внутри зашифрованного JSON: при `SECRET_MAX_SIZE` = 1 MiB максимальный файл — около 750 КБ.

PostgreSQL публикуется только на `127.0.0.1`: Docker обходит правила ufw, и привязка к `0.0.0.0` открыла бы базу в сеть. Подключиться к базе с машины сервера (например, из pgAdmin) можно по `localhost:5433`. Секреты в ней — шифротекст.

## TLS

Сертификаты выпускает собственный CA проекта. Перечислите все имена и IP, по которым клиенты будут подключаться; `localhost` нужен для административного порта.

```bash
make certs CERT_HOSTS=localhost,127.0.0.1,203.0.113.10,keeper.example.com
```

При первом запуске `make certs` создаёт CA и спрашивает пароль для его ключа. Получаются файлы:

| Файл | Назначение |
| --- | --- |
| `certs/ca.crt` | Корневой сертификат. Копируется на все клиентские устройства |
| `certs/server.crt`, `certs/server.key` | Сертификат и ключ сервера, каталог монтируется в контейнер |
| `ca/ca.key` | Ключ CA, зашифрованный паролем. В контейнер не попадает |

Повторный `make certs` перевыпускает сертификат сервера тем же CA (например, чтобы добавить адрес), `ca.crt` у клиентов остаётся прежним. После перевыпуска перезапустите сервер: `docker compose restart gophkeeper`.

**Храните ключ CA отдельно от сервера.** С `ca.key` можно выпустить сертификат, которому поверят все ваши клиенты, и перехватывать их трафик. Утечка `server.key` исправляется перевыпуском сертификата, утечка `ca.key` — только новым CA и заменой `ca.crt` на всех устройствах. После выпуска перенесите `ca/ca.key` на внешний носитель и возвращайте только для `make certs`.

Если `TLS_CERT_FILE` и `TLS_KEY_FILE` пусты, сервер работает без TLS и пишет предупреждение в лог. Клиенты подключатся к нему только с `GOPHKEEPER_INSECURE=true`. Это режим для локальной разработки: ключ аутентификации и токены идут открытым текстом.

## Регистрация и администрирование

По умолчанию регистрация открыта: зарегистрироваться может любой, кто достучится до сервера. Для личного или семейного сервера её лучше закрыть:

```env
REGISTRATION_ENABLED=false
ADMIN_PORT=50052
```

Тогда регистрация на публичном порту отклоняется, а учётки создаются через административный порт. Он публикуется только на `127.0.0.1`, поэтому доступен лишь с машины сервера; пароль администратора не нужен.

```bash
export GOPHKEEPER_SERVER=localhost:50052

gophkeeper auth register alice              # своя учётка
gophkeeper auth register bob --temporary    # учётка для другого человека
# Временный пароль для bob: k7Rp-x2Mq-9vTz-L4wN
# Действует до 2026-10-10 14:00. При первом входе пользователь задаст свой пароль.
```

Временный пароль передайте надёжным каналом. При первом входе пользователь задаёт свой пароль, ключи выводятся из него с новой солью, и администратор, знавший временный пароль, доступа к учётке больше не имеет. До смены пароля вход разрешает только смену пароля и выход. Если временный пароль перехватили и вошли первым, владелец не сможет войти: удалите учётку и создайте заново — данных в ней ещё нет.

Управление пользователями:

```bash
gophkeeper admin list-users              # логин, дата, число секретов, статус пароля
gophkeeper admin user-info bob           # подробности, включая параметры Argon2id
gophkeeper admin revoke-sessions bob     # завершить все сессии, например при потере устройства
gophkeeper admin delete-user bob         # удалить вместе с секретами
```

То же есть в десктоп-приложении: если в настройках указать `localhost:50052`, вместо хранилища открывается панель администратора. Чтобы пользоваться на одной машине и хранилищем, и панелью, держите для панели отдельный каталог данных: `GOPHKEEPER_DESKTOP_DIR=~/.config/GophKeeper-admin`.

Что важно знать:

- **Сбросить пароль нельзя.** Секреты зашифрованы ключом из пароля пользователя. Забытый пароль — это удаление учётки и новая с временным паролем, секреты пропадут.
- `revoke-sessions` не меняет пароль и секреты: на всех устройствах понадобится снова ввести мастер-пароль.
- Удаление необратимо: секреты удаляются вместе с учёткой, токены сразу перестают действовать, логин освобождается. Пользователь может удалить свою учётку сам (`gophkeeper auth delete-account`), для этого нужен мастер-пароль.

## Резервные копии

Сервис `backup` запускается вместе с сервером и сохраняет копию базы (`pg_dump`) в `backups/`: сразу при старте и затем каждые `BACKUP_INTERVAL`, оставляя `BACKUP_KEEP` последних. Файлы принадлежат пользователю, запустившему `make docker-up`, права — `0600`.

```bash
make backup                                          # копия сейчас → backups/manual-<время>.dump, ротацией не удаляется
make restore FILE=backups/gophkeeper-<время>.dump    # восстановить, спросит подтверждение
```

`restore` останавливает сервер, восстанавливает базу одной транзакцией (при ошибке база не меняется) и запускает сервер. Всё, что создано после копии, пропадёт. Все сессии завершаются, иначе токены, отозванные после создания копии, снова стали бы действительными: пользователям нужно один раз ввести мастер-пароль.

**Храните копии не только на сервере** — от поломки диска локальные копии не спасут:

```bash
rsync -a backups/ user@другой-хост:gophkeeper-backups/
```

Секреты в копиях зашифрованы ключами пользователей, поэтому утечка копии равна утечке базы: прочитать секреты нельзя, возможен только офлайн-перебор паролей, замедленный Argon2id.

Независимо от этого пользователь может сделать собственную копию — зашифрованный экспорт (`gophkeeper export`), который импортируется на любом сервере.

## Миграции

Сервис `migrate` применяет новые миграции при каждом `make docker-up`.

| Миграция | Что делает |
| --- | --- |
| `000001_init` | Таблицы `users` и `secrets` |
| `000002_auth_key_hash` | Хеши паролей в формате `SHA-256(authKey)`. Необратима |
| `000003_token_revocation` | Версия токенов у пользователя и таблица отозванных токенов |
| `000004_kdf_params` | Параметры Argon2id у каждого пользователя |
| `000005_temporary_passwords` | Срок действия временного пароля |

Откатить последнюю миграцию:

```bash
docker compose --profile tools run --rm migrate-down
```

## Образ сервера

CI собирает образ `ghcr.io/f3dosik/gophkeeper` для amd64 и arm64 и публикует его после прохождения тестов:

| Событие | Теги образа |
| --- | --- |
| Коммит в `main` | `sha-<7 символов коммита>`, `main` |
| Релиз `vX.Y.Z` | `X.Y.Z`, `X.Y`, `latest` |

`make docker-up` выбирает тег по текущему коммиту каталога: на теге релиза — `X.Y.Z`, иначе — `sha-<коммит>`. Так сервер всегда той же версии, что миграции и `docker-compose.yaml` рядом с ним. Используемый образ печатается при запуске. Другую версию можно задать явно: `make docker-up SERVER_TAG=1.2.0`.

Если образа для коммита нет — CI ещё не закончил сборку (несколько минут после push) или коммита нет в `main` — `make docker-up` сообщит об этом. Тогда сервер можно собрать из исходников:

```bash
make docker-up-local      # сборка на этой машине, нужно 700–900 МБ свободной памяти
```

На VPS с 1 ГБ памяти для сборки из исходников понадобится swap.

## Обновление

На сервере удобнее держать последний релиз:

```bash
make backup
git fetch --tags && git checkout v1.2.0   # нужный релиз
make docker-up                             # скачает образ 1.2.0 и применит новые миграции
```

Или следовать за `main`: `git pull && make docker-up`.

Данные сохраняются. Клиенты обновите до той же версии: готовые сборки — в [Releases](https://github.com/F3dosik/GophKeeper/releases).
