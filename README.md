# GophKeeper

Клиент-серверный менеджер паролей и приватных данных. Сервер работает в Docker, клиент — кроссплатформенный CLI-бинарь.

## Возможности

- Регистрация и аутентификация пользователей (JWT).
- Хранение секретов четырёх типов: `credentials`, `text`, `card`, `binary`.
- Клиентское шифрование: AES-256-GCM с ключом, производным от пароля (Argon2id + HKDF); сервер видит только шифротекст.
- Разделение ключей: на сервер уходит только ключ аутентификации, из которого нельзя получить ключ шифрования (см. [Схема ключей](#схема-ключей)).
- TLS между клиентом и сервером, на клиенте включён по умолчанию.
- Проверка мастер-пароля на сервере перед каждой операцией с секретами.
- Проверка целостности: клиент обнаруживает, если сервер подменил один секрет другим.
- Короткоживущие JWT с отзывом на сервере: выход на одном или на всех устройствах.
- Ограничение частоты запросов к аутентификации и квоты на хранение секретов.
- Поиск по имени через blind index (HMAC-SHA256).
- CRUD-операции над секретами, листинг с фильтрацией по типу.

Подробнее о модели угроз — в разделе [Безопасность](#безопасность).

## Структура

- `cmd/client`, `cmd/server` — точки входа.
- `internal/client` — CLI (Cobra), gRPC-клиент, сервисный слой, сессия.
- `internal/server` — gRPC-хендлеры, сервисы, репозитории (pgx), JWT, логгер.
- `internal/domain` — модели и доменные ошибки.
- `pkg/crypto` — примитивы шифрования.
- `proto/` — схемы gRPC, `proto/gen` — сгенерированный код.
- `migrations/` — SQL-миграции (golang-migrate).
- `tests/e2e` — интеграционные тесты на testcontainers-go.

## Переменные окружения

### Сервер (`.env`)

| Переменная     | Описание                                         | Пример                                                      |
| -------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| `DATABASE_URL` | DSN PostgreSQL                                   | `postgresql://gophkeeper:secret@db/gophkeeper?sslmode=disable` |
| `JWT_SECRET`   | Секрет для подписи JWT (≥ 32 символа)            | `your-super-secret-key-min-32-chars`                        |
| `SERVER_PORT`  | Порт gRPC-сервера (по умолчанию `50051`)         | `50051`                                                     |
| `LOG_LEVEL`    | `development` или `production`                   | `development`                                               |
| `TOKEN_TTL`    | Время жизни JWT (по умолчанию `1h`)              | `30m`, `1h`                                                 |
| `TLS_CERT_FILE`| Сертификат сервера (PEM), путь внутри контейнера | `/certs/server.crt`                                         |
| `TLS_KEY_FILE` | Приватный ключ сервера (PEM)                     | `/certs/server.key`                                         |

| Переменная         | Описание                                                        | По умолчанию |
| ------------------ | --------------------------------------------------------------- | ------------ |
| `AUTH_RATE_LIMIT`  | Запросов к `GetSalt`/`CreateUser`/`Login` в минуту с одного IP  | `30`         |
| `AUTH_RATE_BURST`  | Таких запросов подряд с одного IP                               | `20`         |
| `SECRET_MAX_SIZE`  | Максимальный размер зашифрованного секрета, байт                | `1048576`    |
| `SECRET_MAX_COUNT` | Максимум секретов у одного пользователя                         | `1000`       |
| `REGISTRATION_ENABLED` | Разрешить регистрацию на публичном порту                    | `true`       |
| `ADMIN_PORT`       | Административный порт (регистрация и временные пароли); пусто — выключен | —   |
| `TEMP_PASSWORD_TTL`| Срок действия временного пароля                                 | `24h`        |

`SECRET_MAX_SIZE` не может быть больше 32 MiB: клиент принимает ответы до 64 MiB. Список секретов сервер отдаёт страницами (до 100 секретов и около 4 MiB на страницу), клиент собирает их сам.

Лимит частоты замедляет онлайн-перебор паролей и массовую регистрацию, квоты не дают заполнить диск сервера. Каждая операция с секретами проверяет мастер-пароль и делает 2 запроса к `Auth`, поэтому при значениях по умолчанию с одного IP можно выполнить 10 операций подряд и около 15 в минуту; `auth passwd` делает 3 запроса. Бинарные секреты хранятся в base64 внутри JSON, поэтому при `SECRET_MAX_SIZE` = 1 MiB максимальный размер файла около 750 КБ.

`TLS_CERT_FILE` и `TLS_KEY_FILE` задаются вместе. Если оба пусты, сервер работает без TLS и пишет предупреждение в лог. Так можно делать только при локальной разработке.

Пример — см. [`.env_example`](.env_example).

### Клиент

| Переменная             | Описание                                     | По умолчанию            |
| ---------------------- | -------------------------------------------- | ----------------------- |
| `GOPHKEEPER_SERVER`    | Адрес gRPC-сервера                           | `localhost:50051`       |
| `GOPHKEEPER_SESSION`   | Путь к файлу сессии (хранит логин и токен)   | `~/.gophkeeper/session` |
| `GOPHKEEPER_TLS_CERT`  | Путь к CA-сертификату для TLS (опционально)  | —                       |
| `GOPHKEEPER_INSECURE`  | `true` — подключаться без TLS                | `false`                 |

Клиент всегда подключается по TLS. Если задан `GOPHKEEPER_TLS_CERT`, сертификат сервера проверяется этим CA, иначе системными корневыми сертификатами. Без TLS клиент подключается только при `GOPHKEEPER_INSECURE=true` и в этом случае выводит предупреждение. Такой режим подходит только для локальной разработки: ключ аутентификации и токен идут открытым текстом. Одновременно задать `GOPHKEEPER_INSECURE` и `GOPHKEEPER_TLS_CERT` нельзя.

## Запуск сервера

```bash
cp .env_example .env  # заполнить значения
make docker-up        # поднимает postgres, применяет миграции, запускает сервер
make docker-down
```

Postgres публикуется только на `127.0.0.1:5433`: Docker обходит правила ufw, поэтому привязка к `0.0.0.0` открыла бы базу в сеть.

Миграции применяет сервис `migrate` при каждом `make docker-up`:

| Миграция                   | Что делает                                                                      | Откат                       |
| -------------------------- | ------------------------------------------------------------------------------- | --------------------------- |
| `000001_init`              | Таблицы `users` и `secrets`                                                      | Удаляет таблицы             |
| `000002_auth_key_hash`     | Переводит хеши паролей на `SHA-256(authKey)` (см. [Схема ключей](#схема-ключей)) | Необратима, `down` ничего не делает |
| `000003_token_revocation`  | `users.token_version` и таблица `revoked_tokens` для отзыва токенов              | Удаляет добавленное         |
| `000004_kdf_params`        | Параметры Argon2id у каждого пользователя, существующим — прежние `t=1`          | Удаляет столбцы; пользователи с другими параметрами не смогут войти |
| `000005_temporary_passwords` | Срок действия временного пароля (`users.password_expires_at`)                  | Удаляет столбец             |

### Обновление существующей установки

```bash
git pull
make docker-up        # пересоберёт образ и применит новые миграции, данные в volume сохранятся
```

- Пересоберите клиент на всех устройствах (`make build-client` или `go build` в Termux) и один раз выполните `auth login`: токены старого формата новый сервер не принимает.
- Если в `.env` задан `TOKEN_TTL=24h`, уменьшите его до `1h`: значение из `.env` важнее значения по умолчанию.
- Если клиент раньше подключался без `GOPHKEEPER_TLS_CERT`, задайте его: без него клиент проверяет сертификат сервера системными корневыми сертификатами и не примет самоподписанный.

## TLS и удалённый доступ

Если сервер доступен по сети, включите TLS. Сертификаты выпускает собственный CA проекта:

```bash
# перечислите все имена и IP, по которым клиенты будут обращаться к серверу
make certs CERT_HOSTS=localhost,127.0.0.1,203.0.113.10,keeper.example.com
```

При первом запуске `make certs` создаёт CA и спрашивает пароль для его ключа. Появятся файлы:

- `certs/ca.crt` — корневой сертификат. Его нужно передать на клиентские машины.
- `certs/server.crt`, `certs/server.key` — сертификат и ключ сервера, каталог `certs/` монтируется в контейнер.
- `ca/ca.key` — ключ CA, зашифрованный паролем. Каталог `ca/` в контейнер не монтируется.

Повторный `make certs` перевыпускает сертификат сервера тем же CA и спрашивает пароль ключа CA. `ca.crt` у клиентов менять не придётся. Если пароль неверный, текущий сертификат не меняется.

**Храните ключ CA отдельно от сервера.** Тот, у кого есть `ca.key`, может выпустить сертификат, которому поверят все ваши клиенты, и перехватывать их трафик. Утёкший `server.key` исправляется перевыпуском сертификата, а после утечки `ca.key` придётся создавать новый CA и заново раздавать `ca.crt` на все устройства. После выпуска сертификата перенесите `ca/ca.key` на флешку или в менеджер паролей и возвращайте его только для `make certs`.

Если CA создан старой версией проекта, ключ лежит в `certs/ca.key` без пароля. `make certs` в этом случае откажется работать и подскажет, как перенести и зашифровать ключ:

```bash
mkdir -p ca && mv certs/ca.key ca/ && make ca-encrypt
```

На удалённой машине:

```bash
export GOPHKEEPER_SERVER=203.0.113.10:50051     # адрес должен входить в CERT_HOSTS
export GOPHKEEPER_TLS_CERT=/path/to/ca.crt
gophkeeper auth login alice
gophkeeper secret get --name gmail --type credentials
```

Соль хранится на сервере, ключи выводятся из пароля, поэтому секреты, созданные на одной машине, читаются на любой другой под той же учёткой.

## Сессии и отзыв токенов

После `auth login` клиент хранит JWT в файле сессии. Каждая операция с секретами проверяет мастер-пароль на сервере и получает новый токен, поэтому срок жизни токена можно держать коротким (`TOKEN_TTL`, по умолчанию 1 час): если файл сессии украдут, токен скоро истечёт сам.

Токены можно отозвать раньше срока:

- `auth logout` отзывает токен текущего устройства (его `jti` попадает в таблицу `revoked_tokens`);
- `auth logout --all` отзывает все токены пользователя (увеличивается `users.token_version`). Используйте эту команду, если устройство потеряно или файл сессии мог утечь.

Сервер проверяет отзыв при каждом запросе.

## Регистрация пользователей

По умолчанию регистрация открыта: любой, кто может подключиться к серверу, выполняет `auth register`. Для личного сервера её лучше закрыть:

```env
REGISTRATION_ENABLED=false
ADMIN_PORT=50052
```

Тогда `CreateUser` на публичном порту отвечает `PermissionDenied`, а регистрировать можно только через административный порт. Он публикуется на `127.0.0.1` и доступен только с машины сервера. Сертификат сервера должен включать `localhost` (так `make certs` делает по умолчанию).

Зарегистрировать себя — на машине сервера:

```bash
GOPHKEEPER_SERVER=localhost:50052 gophkeeper auth register alice
```

Завести учётку для другого человека — с временным паролем:

```bash
GOPHKEEPER_SERVER=localhost:50052 gophkeeper auth register bob --temporary
# Временный пароль для bob: k7Rp-x2Mq-9vTz-L4wN
# Действует до 2026-10-10 14:00. При первом входе пользователь задаст свой пароль.
```

Передайте временный пароль надёжным каналом. При первом `auth login bob` клиент попросит задать свой пароль: клиент выводит из него новые ключи с новой солью, поэтому администратор, знающий временный пароль, после смены доступа к учётке не имеет. Пока пароль не сменён, токен действует 10 минут и разрешает только смену пароля и выход, а файл сессии не сохраняется. Временный пароль можно использовать до истечения `TEMP_PASSWORD_TTL`; если кто-то перехватит его и войдёт первым, владелец не сможет войти — пересоздайте учётку (данных в ней ещё нет).

## Смена пароля

`gophkeeper auth passwd` спрашивает текущий и новый пароль. От пароля зависят ключ шифрования и blind index, поэтому клиент:

1. скачивает все секреты и расшифровывает их ключом от текущего пароля (с проверкой целостности);
2. генерирует новую соль, выводит ключи из нового пароля с актуальными параметрами Argon2id;
3. шифрует секреты новым ключом, пересчитывает blind index и отправляет всё одним потоком.

Сервер проверяет текущий пароль и в одной транзакции заменяет соль, параметры, хеш и все секреты. Если что-то пошло не так (обрыв связи, неверный пароль, ошибка БД), ничего не меняется. Если во время смены другое устройство создало, изменило или удалило секрет, смена отменяется с просьбой повторить: иначе такой секрет остался бы со старыми ключами и стал нечитаемым.

После смены все токены пользователя отзываются: на остальных устройствах нужно снова выполнить `auth login`. Смена пароля — это и способ перевести старую учётку на более сильные параметры Argon2id, и действие на случай, если пароль мог утечь.

## Схема ключей

```
masterKey = Argon2id(пароль, соль, параметры) # только на клиенте
authKey   = HKDF(masterKey, "auth")         # отправляется на сервер при register/login
encKey    = HKDF(masterKey, "encryption")   # AES-256-GCM, только на клиенте
hmacKey   = HKDF(masterKey, "blind-index")  # blind index, только на клиенте
```

Соль и параметры Argon2id хранятся у каждого пользователя и приходят клиенту в `GetSalt`. Новые пользователи получают `t=3, m=64 MiB, p=4` (RFC 9106). Пользователи, созданные до миграции `000004_kdf_params`, сохраняют прежние `t=1`, поэтому их ключи не меняются; более сильные параметры они получат при смене пароля. Клиент отказывается работать с параметрами вне допустимых границ, чтобы подменённый сервер не мог ни ослабить деривацию, ни заставить клиент считать часами.

Параметры можно выбрать флагами `--kdf-time` (1–10 проходов) и `--kdf-memory` (19–1024 MiB) у `auth register` и `auth passwd`; по умолчанию `t=3`, 64 MiB. Больше проходов и памяти — дороже перебор пароля при утечке БД, но и медленнее каждый вход и каждая операция с секретами (Argon2id считается на клиенте, на телефоне это заметнее). Изменить параметры существующей учётки можно только сменой пароля: от них зависит ключ шифрования. Сервер принимает любые параметры в этих границах.

Сервер хранит `SHA-256(authKey)`. Из `authKey` нельзя восстановить ни `masterKey`, ни `encKey`. Поэтому ни сервер, ни утёкшая БД, ни перехваченный `authKey` не позволяют расшифровать секреты.

Миграция `000002_auth_key_hash` переводит существующих пользователей на эту схему, пароли менять не нужно. Миграция необратима: её `down` ничего не делает, и старая версия сервера после неё не сможет аутентифицировать пользователей.

## Безопасность

| Угроза | Защита |
| --- | --- |
| Утечка БД или компрометация сервера | Секреты шифруются на клиенте. В БД лежат шифротексты и `SHA-256(authKey)`, из которых нельзя получить ключ шифрования. Остаётся офлайн-перебор паролей ценой Argon2id на каждую попытку |
| Перехват трафика | TLS: на сервере включается сертификатом, на клиенте обязателен, если не задан `GOPHKEEPER_INSECURE=true` |
| Онлайн-перебор паролей, массовая регистрация | Лимит частоты запросов к `GetSalt`/`CreateUser`/`Login` с одного IP |
| Заполнение диска сервера | Квоты на размер и количество секретов у пользователя |
| Кража файла сессии | Токен живёт 1 час. `auth logout --all` отзывает все токены сразу. Без мастер-пароля токен даёт доступ только к шифротекстам, но позволяет удалить или перезаписать секреты |
| Подмена секрета сервером | После расшифровки клиент сверяет имя и тип внутри секрета с blind index записи и при расхождении сообщает о нарушении целостности |
| Перебор логинов | Для несуществующего логина `GetSalt` возвращает стабильную фиктивную соль, `Login` отвечает одинаково при неверном логине и неверном пароле |
| Опечатка в мастер-пароле | Пароль проверяется на сервере до шифрования, поэтому секрет не сохранится под ключом от неверного пароля |

Известные ограничения:

- Сервер может вернуть **старую версию** того же секрета или скрыть секрет из списка. Без хранения состояния на клиенте это не обнаружить.
- Сервер видит метаданные: число секретов, время создания и обращения, примерный размер. Открытый текст секрета дополняется до размера, кратного 256 байтам, поэтому по размеру шифротекста не определить длину пароля или короткой заметки, но большой файл от маленького отличить можно. Секреты, созданные до появления дополнения, выравниваются при следующем обновлении или смене пароля.
- `CreateUser` отвечает `AlreadyExists` для занятого логина, поэтому через регистрацию можно проверить, существует ли логин.
- Пользователи, созданные до миграции `000004_kdf_params`, остаются на `t=1`, пока не сменят пароль. Для несуществующих логинов `GetSalt` возвращает параметры новых пользователей, поэтому по `t=1` можно понять, что логин существует и создан давно.

## Использование

```bash
# регистрация и вход
gophkeeper auth register alice
gophkeeper auth login alice
gophkeeper auth logout          # отозвать токен этого устройства
gophkeeper auth logout --all    # отозвать токены на всех устройствах
gophkeeper auth passwd          # сменить мастер-пароль
gophkeeper auth passwd --kdf-time 4 --kdf-memory 128   # с другими параметрами Argon2id

# создание секретов
gophkeeper secret create --name gmail --type credentials
gophkeeper secret create --name passport --type text
gophkeeper secret create --name visa --type card
gophkeeper secret create --name keyfile --type binary

# чтение
gophkeeper secret get --name gmail --type credentials
gophkeeper secret get --name gmail --type credentials --json
gophkeeper secret get --name keyfile --type binary --output ./keyfile.bin

# обновление и удаление
gophkeeper secret update --name gmail --type credentials
gophkeeper secret delete --name gmail --type credentials --yes

# список
gophkeeper secret list
gophkeeper secret list --type card
```

При входе в систему и операциях с секретами клиент интерактивно запрашивает мастер-пароль. Перед операцией с секретами пароль проверяется на сервере: при ошибке клиент сообщает «неверный мастер-пароль» и ничего не шифрует и не отправляет. При успешной проверке клиент получает новый токен, поэтому активному пользователю не нужно повторять `auth login` после истечения `TOKEN_TTL`.

Если вывод `secret get` или `secret list` завершился ошибкой «нарушена целостность», значит, сервер вернул не тот секрет, который запрашивался. Это признак компрометации сервера.

## Разработка

```bash
make generate     # перегенерировать gRPC-код из proto/
make docs         # сгенерировать docs/api.md из .proto (нужен protoc-gen-doc)
make test         # unit-тесты
make test-e2e     # интеграционные тесты (требует Docker)
make test-cover   # покрытие (без mocks/, proto/gen/, cmd/)
make clean        # удалить bin/ и coverage*.out
```

Документация gRPC API собирается из комментариев в `proto/*.proto` и лежит в [`docs/api.md`](docs/api.md).
Установка генератора:

```bash
go install github.com/pseudomuto/protoc-gen-doc/cmd/protoc-gen-doc@latest
```

Для запуска миграции вниз на один шаг:

```bash
docker compose --profile tools run --rm migrate-down
```
